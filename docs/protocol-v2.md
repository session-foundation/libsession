# Session Protocol v2 - design details

This update to the Session protocol aims to add multiple capabilities to Session, with the headline
features being perfect forward secrecy (PFS) and post-quantum (PQ) encryption for 1-1 direct
messages (DMs).

This document breaks down the design into multiple components.

The underlying goal here is protection of DM message content: it should be impossible for someone
with (only) the long-term Session secret key to decrypt past, present, or future messages.
Potential adversaries here are assumed to be able to log all stored swarm messages (e.g. by access
to a swarm storage server) for future decryption if that Session long-term private key is eventually
compromised.

## Linked device configuration

Currently Session config data stored in an account's swarm is encrypted with the long-term Session
encryption key (hereafter referred to as the root key).  While acceptable for some data, this is not
usable for the PFS keys used in DMs as any later compromise of the root key.  The future adversary
with a compromised root key could use that key to decrypt past messages containing temporary
decryption keys, and then use those to decrypt the message contents.

Thus the first part of the protocol is to construct shared keys among linked devices and use these
keys for all PFS-related key storage.

There are two types of messages involved here:
- Shared encrypted data
- Linked device group join handshakes

Shared encrypted data (stored in namespace 21) is where all unique shared encrypted data will be
stored, including keys usable for PFS and PQ.  Join handshakes (also stored in this namespace) will
be used by a new device asking to join the encrypted device group.

The message types share the one namespace rather than being split across several: each is a bt-encoded
dict whose `""` key carries a single-character type tag — `"G"` for a device group message, `"L"`
for a link request, `"T"` for a tombstone dissolving a group (see "Dissolving a group") — so a
client distinguishes them from the message itself rather than from where it was stored.

### Inner device data

The innermost (plaintext) layer is a bt-encoded dict of per-device records.  It is not a
libsession-util config object: config messages derive their encryption key from the account root
key, which would make the data readable by any holder of that key, and a device outside the group
must be able to see and verify a message that it cannot read.

The merge rules follow those of config data: each device writes only its own record, a record is
accepted only if its `seq` exceeds the value already held, and a record absent from a message is
left unchanged rather than removed (see "Removed devices" below).

Device data might consist of the following (but bencoded, not json; note also that the verbose key
names used here are not the actual key names that will be in the encoded data):

    {
        "devices": {
            "unique-client-identifier1": {
                "type": "i",
                "seq": 1234,
                "timestamp": 1777777777,
                "description": "iPhone OS 28 - Alice's phone",
                "version": 2025000,
                "unknown_extra_field": { "x": 123, "y": [1,3,997,"x"] },
                "device_pubkey_x25519": "abcdef123...(32 bytes)",
                "device_pubkey_mlkem768": "...(1184 bytes)..."
            },
            "unique-client-identifier2": {
                "type": "d",
                "seq": 10,
                "timestamp": 1777777778,
                "description": "Linux - betwixt",
                "version": 2000000,
                "device_pubkey_x25519": "987654321...",
                "device_pubkey_mlkem768": "...(1184 bytes)..."
            },
            "unique-client-identifier3": {
                "type": "a",
                "seq": 515,
                "timestamp": 1777777779,
                "description": "Alice's tablet - Android 17",
                "version": 3000007,
                "device_pubkey_x25519": "999666333...",
                "device_pubkey_mlkem768": "...(1184 bytes)..."
            }
        },
        "account_keys": { /* discussed layer */ }
    }

 Where:

- `unique-client-identifier` is the device's 16-byte identifier: random bytes generated by
  libsession when the device first starts, and again whenever the device takes a new identity (see
  "Removed devices").  It is never chosen by the client.  16 bytes keeps the odds of any two devices
  colliding below 2⁻⁶⁴ even across a billion devices, and since every record and tombstone carries
  one, it is kept no longer than that.  The identifier is for uniqueness, not description: there is
  a separate description field for device descriptive details.

- `type` indicates the session platform: "i" for iOS, "a" for Android, "d" for Desktop.  Other
  single-letter values are reserved, but longer (free-form) values are permitted for custom client
  implementations.

- `seq` is a monotonic numeric identifier that a device updates each time it changes its device
  data.  Other devices will ignore any update that is not larger than the most recent value they
  know of.

  A device keeps no counter of its own for it.  What it describes itself as -- description, type,
  version and any later fields -- it keeps apart from the group, and builds every record of its own
  from that and its current device keys.  The group's copy of its record only says what the swarm
  holds for it: when what the device would publish differs from that, its next record is one past
  the held record's `seq`, and otherwise it is the held record.  Nothing in the group's copy flows
  back into what the device publishes, so a record written for it by anyone else is merged like any
  other and simply overtaken by its next push; and a device that has left a group starts again at
  1 in the next, nothing being held for it there.

- `timestamp` is the unix timestamp when the device last updated its data.  Its primary purpose is
  to allow other devices a (very rough) indicator of when a device was last active.  Note that
  clients typically only update this when rotating keys, and so devices should only treat this as a
  device being active sometime recently, and not a precise "last active" timestamp.

- `version` indicates the client version encoded as an integer where application version M.m.p is
  encoded as 1000000×M + 1000×m + p, e.g. the above represent application versions 2.25.0, 2.0.0,
  and 3.0.7, respectively.  "Extra" tags like "-alpha6" and so on are not supported or included.

- `device_pubkey_x25519` and `_mlkem768` are short-term x25519 and MLKEM768 pubkeys, respectively,
  used for encrypting device config messages.  These keys must be randomly generated: they must
  *not* be derivable from any existing account or device keys, and must not be disclosed outside the
  device: someone with both keys will be able to encrypt messages for the device in question (until
  keys rotate).

  Although clients can generate these in any way (i.e. the generation mechanism is opaque to anyone
  outside the device itself) we use a single, random 32-byte value that is expanded into 32+64 byte
  X25519 and ML-KEM seeds using SHAKE256("SessionDeviceKeys" || seed_32B), to align with other key
  expansion (such as for accounts) used elsewhere in this protocol.

- `description` is free-form text describing the device, capped at 64 bytes (`DESCRIPTION_MAX` in
  libsession).  This is a byte limit rather than a character limit; truncation must fall on a UTF-8
  character boundary.  A writer truncates before publishing, and a reader truncates whatever it
  decodes, so that a record from a newer or broken device carrying more is held and shown at the
  cap.  It is the only field of a record not generated by libsession, and so the only one that
  would otherwise leave a record unbounded in size.

- Any other fields (such as `"unknown_extra_field"` in the above example) are preserved rather than
  dropped, so that a device running an older version does not discard fields added by a newer one.
  These are for future versions of libsession rather than for client data: a field added here is
  republished by every device on the account, and must fit within the per-record budget below.

A typical record size is:
    16 + 3 # device ID + encoding overhead
    + 3 + 3 # type encoding
    + 3 + [3-6] # seqno encoding.  6 would be for a 4-digit number, which would be sufficient for years of rotations
    + 3 + 12 # timestamp encoding
    + 3 + 3 + [~28] # Variable: example is for 28-byte "iPhone OS 28 - Alice's phone"
    + 3 + 9 # typical 7-digit version encoding
    + 3 + 3 + 32 # x25519 pk
    + 3 + 5 + 1184 # mlkem768
    ==============
    1325 bytes  (approximate; some field lengths are variable)

A payload also carries the account key list, which is present regardless of the number of devices.
Its size is bounded by the retention and rotation periods: keys rotate every 12h and are retained
for 16 days, giving at most 33 entries of about 70 bytes each — an allowance of **2300 bytes**.

Padding is therefore to a size of:

    2300 + 6400×N

where the 2300 covers the account key list and each 6400-byte bucket covers four devices at a
budget of 1500 bytes per device record, the remainder of the bucket being available for removal
tombstones: a payload carries at most 4 of them for each bucket of live devices (see "Which removals
a message carries").

The budget is not enforced.  Records or account keys exceeding their allowance push the payload into
the next bucket rather than being rejected.

Note that the padded size is not what tells a reader how many devices an account has: the `keys`
list in the outer structure is unencrypted and already gives that count, and is what a storage
server reads to enforce a device limit (see "Extension - Pro subscriptions" below).

### Removed devices

A removed device is written into the devices dict as a tombstone: its ID maps to a small dict saying
how and when it went, in place of the record a live device maps to.

- `{"r": timestamp}` for a device removed by another;
- `{"l": timestamp}` for one that left of its own accord (see "Leaving a group").

The timestamp is the unix time, in seconds, of the removal or departure, and must be positive.  A
tombstone holds exactly one of the two keys.  Every live record carries `seq`, and a tombstone never
does, which is how a reader tells them apart; any other key in a tombstone is ignored, so that later
versions can add to it.  Where two tombstones for the same device differ, a removal beats a
departure, and between two of the same kind the later timestamp wins.

A device holding an existing record for the removed device marks that record removed and retains the
rest of its fields; a device with no record for it ignores the entry.  Since a record absent from a
message is left unchanged rather than removed, a removal must be stated in this way to propagate at
all.

A tombstone and a live record for one device ID cannot coexist, so a device that is removed and
later rejoins the group must take a new device ID, with new device keys to go with it.  It does so
as part of asking to join (or of starting a group): what it held of the group it was removed from
is forgotten at the same time, its account keys included, as for any device leaving a group (see
"Leaving a group").  Its message history, the account seed and configs are all still valid, and
are kept.  It then asks as any device outside a group does.

The removed device is not among the message recipients and cannot decrypt the payload; see
"Announcing removals" below.

Removing a device does not stop it, or any other holder of the account seed, from publishing a
group message of its own: one registering a device it controls, encrypted to the members' device
public keys it knows.  The seed signs whatever its holder likes, and nothing in the protocol
prevents that.  Device key rotation makes the knowledge go stale (see "Device key rotation"): once
the members have rotated, nothing encrypted to the keys it knew is readable by any of them.  Beyond
that the defence is notification, not prevention, as it is for everything a seed holder can do
(see "Displaced devices"): every member tells its user of a device added to the group, and the user
decides what to do about one they do not recognise -- remove it, or, if the seed itself is
compromised, start afresh from a device they trust.

#### Which removals a message carries

A tombstone is there to tell devices that were offline when the removal or departure happened: a
device that saw it already holds it, and keeps it for good.  Blocking the removed device from being
merged back in is not what a tombstone in a message is for: once the members' device keys have
rotated, a removed device can no longer produce a message any of them can read.

So a message does not carry every tombstone ever made.  For a group with N live devices it carries
the 4⌈N/4⌉ most recent -- removals and departures together, by their timestamps -- and none more
than 6 months old.  The cap is the group's bucket of devices, so that removal history stays the
same share of a payload whatever the group's size; a group that shrinks across a bucket boundary
drops its oldest.  This prunes only what a message carries, never what a device holds: a tombstone
left out of messages still decides every merge on a device that has it.

A device offline for longer than that, or across more removals than the cap, is not told by a
tombstone, and has only the fact that it can no longer read its group's messages to go by (see
"Displaced devices").

### Device data encryption

When a client creates or makes any update to the above (which generally should only consist of
changes to its own `unique-client-identifier` record) it then encodes the whole of it -- every group
message is a snapshot of the group, not a diff -- and encrypts it using a random `key_base` value.

Only the device that makes a change pushes for it, and does so at once: it fetches the namespace,
so that what it pushes is built on what the swarm holds, and pushes straight after rather than at
whatever moment it would next have fetched.  One that merges another device's change -- an
admission, a removal -- has nothing to relay: the message carrying it stays in the swarm until a
push carrying its contents forward replaces it, and every member pushing on merging it would only
put that many duplicates there at once.  The others push again on their own schedule (see
"Account Key Rotation").

Note that this random `key_base` value is different from regular config messages: regular config
uses the account root key as the key_base so that other clients with the root key can derive the
encryption key.  That does not work here, however, because this data is encrypted using relatively
short-lived, quantum resistant device keys deliberately not linked to the main key.  Instead we
generate a random key and then encrypt that random key for each linked device.

Before the encryption is actually performed, null byte padding is appended to the encoded value to
bring the plaintext to 2300 + 6400×N bytes (see "Inner device data" above), so that the message size
reveals only which bucket the payload falls in rather than its contents.  A payload consisting of 1
through 4 devices therefore encrypts to an identical size.  On decryption the trailing null bytes
are stripped; the payload is a bt-encoded dict, which always ends in `e`, so trailing nulls are
unambiguously padding.

The 32-byte symmetric encryption key, `key_base`, is itself separately encrypted for each device as
described below.  This process involves generating a single ephemeral X25519 keypair and per-device
ML-KEM ciphertexts and including those on the outside of the message.

This encrypted config message gets stuffed into another bt-encoded message at this point, encoded
as:

```json
    {
        "": "G",
        "@": "...encrypted 8-byte group identifier...",
        "A": "pubkey...",   // ephemeral X25519 pubkey
        "C": "[ct123...][ct456...][ct789...][ctabc...]",
        "K": "[abc123...][def456...][789aaa...][888bbb...]",
        "X": "...the group's current account X25519 pubkey...",
        "d": "...encrypted payload...",
        "k": "[k123...][k456...][k789...][kabc...]",
        "t": 1777777777123,  // when the author wrote it, unix milliseconds
        "~": "...above data signed with long-term account key...",
    }
```

where, under the names the rest of this document uses for them:
- `d`, the `payload`, contains the encrypted payload the device needs, using xchacha20-poly1305
  encryption with the random base key, `key_base`.
- `A` is a single ephemeral X25519 key used for symmetric encryption keys
- `@`, the `group`, identifies which of the account's device groups the message belongs to; see
  "Group identifier" below.
- `k`, the `kicked` list, announces removals to devices that can no longer read the payload; see
  "Announcing removals" below.  It carries no more removals than the payload does (see "Which
  removals a message carries"), and is left out altogether when that is none.
- `X`, the `link_x25519`, is the X25519 half of the group's current account key (see "Account
  keys"), to which a device asking to join the group encrypts its link request (see "Initiating a
  device link").  Only members hold the matching secret, so only they can read requests.  The
  ML-KEM half is not published here: it would add over a kilobyte to every group message, to
  protect a request that lives 10 minutes.  Someone recording requests today for a future quantum
  computer could recover from one the requesting device's description, type and version, and its
  device public keys: metadata tying that device to the account.  That is all.  It gives no access
  to any message, past or future: the keys a request carries are public keys, and nothing in it
  decrypts anything.
- `t`, the `time`, is when the message was written, by its author's clock, in unix milliseconds.
  It is covered by the signature, so unlike the timestamp the swarm reports for a stored message --
  which nothing binds to the message, and which a storage server can set to anything -- it cannot
  be changed by anyone without the account seed.  Wherever a device needs a group message's age, it
  uses this and never the swarm's timestamp: to tell whether it has been displaced (see "Displaced
  devices"), for when a group was last active, and for which of a group's messages carries its
  current `link_x25519`.  A message without `time` is invalid, and one whose `time` is more than 10
  minutes ahead of the reader's clock is ignored: that is a broken clock or a forgery rather than
  clock skew, and believed, it would outrank every honest message from the group until the
  reader's clock caught up.  The swarm's expiry, by contrast, is still what says how long a group's
  message stays stored.
- `C`, the `ciphertexts`, is a packed binary value of 4⌈N/4⌉×1088 bytes, for the N devices the
  message is encrypted to, where each 1088 byte segment contains an ML-KEM768 ciphertext for one of
  them.  When the number of devices is not a multiple of 4, the unused slots are filled with random
  data.
- `K`, the `keys`, are the encrypted values of `key_base`, encrypted for each device using xchacha20
  (NB: this stage of encryption does *not* include poly1305 authentication) with a unique device key
  (described below).  Each entry is 34 bytes: a 2-byte device key index followed by the 32-byte
  encrypted key.  Like `ciphertexts`, this is always a multiple of 4 entries (i.e. 4×34 bytes),
  with random noise used for unused slots.  The entries here must be in the same order as
  `ciphertexts`: that is, the 3rd 1088-byte slice of `ciphertexts` is the ciphertext for the device
  whose encrypted value is the 3rd 34-byte entry of `keys`.
- `""` is the message type tag (see "Linked device configuration"), and `~` the signature, by the
  account's long-term key, over everything before it.

Actual encryption is performed as follows:

1. For each device 𝑖 ∈ {1, ..., 𝑁}, use its pubkey to generate an encapsulated MLKEM-768 secret for that device.

        sᵢ, cᵢ = one encapsulated secret + ciphertext for device i's MLKEM pubkey

2. Pad the ciphertexts as needed with random values of the same length to bring it up to the next
   multiple of 4 ciphertexts:

        cᵢ = random(1088), 𝑖 ∈ {𝑁+1, ..., 4⌈𝑁/4⌉}

3. Generated a shuffled ordering over the 4⌈𝑁/4⌉ elements (and store it; it will be used again in a
   later step), and build the final packed ciphertext value by concatenating all of the cᵢ values
   together in shuffled order:

        ciphertexts = cⱼ || cₖ || cₗ | ...

4. Generate an ephemeral X25519 keypair, a/A.

5. Generate the deterministic nonce for the encrypted `payload` value:

        payload_nonce = BLAKE2b_24(ciphertexts, key=A, pers="SessionDevDNonce")

6. Generate a secure random 32-byte device key for encrypting the padded payload data.

        key_base = random(32)

7. Encrypt the payload data:

        enc_payload = XChaCha20Poly1305(plaintext_payload, key=key_base, nonce=payload_nonce)

8. For each real device (i.e. not the dummy padding entries), calculate the base key encryption
   nonce as:

        knonceᵢ = BLAKE2b_24(ciphertextᵢ || enc_payload, key=A, pers="SessionDevKNonce")

9. Calculate the per-device symmetric encryption key for `key_base` for each device i as follows.
   Given:

        a, A = X25519 keypair from step 4.
        sᵢ, cᵢ = one encapsulated secret + ciphertext from step 2.
        Bᵢ = device's current X25519 pubkey
        Mᵢ = device's current MLKEM pubkey

    the key is encrypted using:

        kᵢ = BLAKE2b_32(aBᵢ || A || Bᵢ || sᵢ || Mᵢ, pers="SessionDevKeyKey")
        keyᵢ = XChaCha20(message=key_base, key=kᵢ, nonce=knonceᵢ)

    This key is prefixed with a two-byte device key index, computed as:

        dkᵢ = BLAKE2b_2(A || Bᵢ || Mᵢ || cᵢ || keyᵢ, pers="SessionDevKeyIdx")

    This indicator is effectively a cheap checksum designed to short-circuit shared secret
    calculation attempts without revealing anything identifying to outside observers: by computing a
    much cheaper hash before attempting the full MLKEM decapsulation + X25519 + XChaCha20 + poly1305
    full payload decryption, it can instead short-circuit almost all encrypted values not meant for
    it, while still revealing nothing to outside observers (because the device MLKEM and X pubkeys
    are not known outside the device group itself).

    Note that this key value is *not* authenticated aside from this checksum (i.e. it is just
    XChaCha20, not XChaCha20+poly1305): authentication happens as part of the final `devices`
    ciphertext decryption, and so does not need to be included here: if the final decryption failed,
    that indicates that the key decryption was not correct (or that the message was tampered with).

10. Pad the key list as needed with random values of the same length to bring it up to the next
    multiple of 4 ciphertexts:

        dkᵢ || keyᵢ = random(2+32), 𝑖 ∈ {𝑁+1, ..., 4⌈𝑁/4⌉}

11. All 4⌈𝑁/4⌉ keyᵢ values (i.e. real + dummy) are then packed in the same shuffled ordering used in
    step 3 into a packed `keys` value:

        keys = dkⱼ || keyⱼ || dkₖ || keyₖ || dkₗ || keyₗ | ...

The final message is then constructed as described above for upload to the swarm.  Note that there
is no additional encryption: the outer structure here is intentionally visible.

This message is then uploaded to the swarm.  If the message contains more than 4 ciphertexts/keys
then the upload request must prove Pro status to the receiving swarm member (otherwise storage
server will reject it for being too large).

(Note that the Pro restriction will likely not be imposed in the initial PFS release)

### Announcing removals

A removed device is not among the message recipients and so cannot decrypt the payload containing
its tombstone.  It is not given a key for that message either: the payload contains the account key
list, including any key generated as part of the removal.

Removals are instead announced in the `kicked` field of the outer, unencrypted structure.  Each
entry is:

    kickᵢ = BLAKE2b_16(seed || deviceidᵢ, key=A, pers="SessionDevKicked")

where `seed` is the account root seed and `A` is the message's ephemeral X25519 pubkey.

A removed device computes this value for its own device ID to detect its removal, and a device that
cannot read a message from its group computes it for the removals it knows of, to tell whether it
was displaced instead (see "Displaced devices").  Devices still in the group take removals from the
tombstones in the payload and have no use for this field.  Without the root seed the entries are
indistinguishable from random.

The list is built from the removals among the tombstones the payload carries, and so is bounded by
the same cap (see "Which removals a message carries") -- never from departures, since a device that
left already knows, and would otherwise read its own departure as a removal -- recomputed for each
message: the entries
cannot be recovered from a previous message, since a device ID cannot be derived from an entry and
the value depends on that message's `A`.

`A` is included so that the entries differ from message to message.  Computed without it an entry
would be constant for a given device ID, and the real entries could be identified as those appearing
in two consecutive messages.

The list is padded to a multiple of 4 entries with random values and shuffled, as `ciphertexts` and
`keys` are, so that its length indicates only which bucket the removal count falls in.

An adversary who obtains the root seed can compute these values, and so recover an account's removal
history from stored messages.

### Displaced devices

A device can also lose its place without being removed: another device comes to hold its record,
under its device ID, with keys it does not have.  That happens when a restored copy of it is
admitted as a replacement (see "Device link request handling"), and when someone holding a copy of
its data -- device keys and all -- rotates those keys and pushes the record.  The second is an
attack, and the design deliberately settles it in favour of whichever copy rotates first: the other
can read nothing after that.  If the real device rotates first, the copy is shut out, which is the
point; if the copy does, the real device must notice and say so.

It can: while it is in the group, every message from the group is encrypted to it, so one carrying
its group's identifier that it cannot decrypt means the group has moved on without it.  The
message's `kicked` list says why, as far as it can.  The device computes the entry for its own ID,
and for every removed device it holds a tombstone for -- of any age, since it keeps them all --
under the message's `A`:

- Its own entry is there: it was **removed** (see "Announcing removals").
- Its own is not, but the entry of a removal it already knew of is: it was **displaced**.  A message
  carries its group's most recent removals, so one still carrying a removal from before the device
  lost the group carries every removal made since, and the device's own would be among them.
- There is no `kicked` list at all, and the device last read the group less than 6 months before
  the message was written: also **displaced**.  The group has removed nobody in that time, so not
  this device.
- Otherwise -- a list of nothing it knows, or none after longer away than removals are carried --
  it cannot tell whether it was removed, replaced, or only away too long, and is **dropped** (see
  "Forks").

How many removals since the device last read its group lose it the distinction is set by the cap
on what a message carries (see "Which removals a message carries").  A group of N live devices
carries its 4⌈N/4⌉ most recent removals and departures, so once that many have been made since the
newest removal the device knows of, that removal is no longer carried, and with it goes the proof
that the device's own would have been.

A displacement or a drop counts only if the message's `time` is more than 5 minutes past that of the
newest message from the group the device *could* read.  The signed `time`, not the swarm's
timestamp: otherwise a storage server could keep an old message the device was never able to read
-- from before it joined, say -- and replay it under a later date to raise a false alert, or re-date
a readable one far ahead to hide a real displacement.  Just after a device joins, a member may push
a snapshot it built before fetching the admission, which leaves the new device out for no reason
but timing, and the margin also absorbs the difference between the two devices' clocks.  It costs
nothing in detection: every later message is unreadable too, and account key rotation guarantees
one.  A removal needs no margin: nothing written before the device joined names its ID, which is new
to every group it joins (see "Removed devices").

A displaced device alerts its user, as a possible attack, and stops acting for the group: it pushes
nothing, admits and removes nobody, and pushes no departure if it leaves the group, since a
departure under its ID would now apply to the device holding it.  It can come back only under a new
device ID, which it takes, as a removed device does, as part of asking to join again.  A dropped
device stops acting for the group in the same way, since it may have been displaced, and comes back
the same way, but tells its user only that it is no longer in the group.  Reading a message from
the group again, as new as the one that displaced or dropped it, undoes either.

A holder of the account seed can forge a message carrying the group's identifier, with whatever
`kicked` list it likes, and by leaving the list out have every member of the group conclude that it
was displaced.  That is one of many things the seed lets its holder do to the account: it can as
well delete any of the account's messages, publish account keys of its own in place of the
account's, register a device of its own in the group (see "Removed devices"), or dissolve every
group the account has.  The protocol does not try to prevent any of them, and could not: the
account's user, restoring onto a new device, must be able to do each one.  What it does for those
that reach the device group, or the key contacts encrypt to, is make them seen: a device added is
announced to every member, a dissolution leaves each device of the group dissolved and saying so, a
key published in place of the account's is reported by every device that sees it (see "Rogue
keys"), and a forged displacement is no quieter than a real one -- every member alerts its user, as
a possible attack, and the user decides what happened.  The forger gains nothing else by it: the
devices stop acting for their group, rather than starting to trust anything new.

### Group identifier

Each device group has an identifier, generated when the group is created and never changed
afterwards: rotating keys, and adding or removing devices, all leave it alone.  It is what tells one
group's messages from another's when an account forks (see "One group per account" below),
it gives a user a way to check by eye that two devices are in the same group, and it says roughly
when a group was created, so that one a device has not seen before can be shown with its age.

The identifier is 8 bytes: the creation time in minutes since the unix epoch as a little-endian
32-bit integer, followed by 4 random bytes.  Devices compare all 8 bytes, so two groups created in
the same minute are told apart by the random half.

It is shown as a SAS by the same mechanism as a link request's (see "Handshake short authentication
string"), from a 16-byte seed hashed from the identifier rather than from the identifier itself, so
that groups created close together do not look alike:

    seed = BLAKE2b_16(identifier, pers="SessionDvGrp_SAS")

from which the 21 emoji are taken exactly as for a link request.  The suggested basic display is the
first 4 of them together with the creation time; the full 21 are there for an extended view.  Two
groups sharing a displayed SAS affects only what a user sees, never what a device decides, since
devices compare identifiers rather than emoji.

Four emoji rather than the seven of a link SAS is deliberate, so that the two are not mistaken for
each other at a glance; the creation time shown beside them does most of the work of telling an
account's groups apart.  Nor is the seed memory-hard as a link SAS's is: anyone holding the account
seed can copy a group's identifier outright, so there is nothing for Argon2 to protect.  The
identifier tells groups apart for honest devices and for the user's eye; it does not authenticate
one, and its creation time is whatever the creating device's clock said.

Every group message carries it, and one without is invalid: a device in a group always has its
identifier, from when the group was created or from the message that admitted it.

It is carried in the outer structure, encrypted so that any device holding the account seed can
read it -- including one not yet in any group -- while to anyone else it differs from message to
message:

    k     = BLAKE2b_32(seed, pers="SessionDvGrpID_K")
    nonce = BLAKE2b_24(A, pers="SessionDvGrpID_N")
    group = XChaCha20(identifier, key=k, nonce=nonce)

where `seed` is the account root seed and `A` is the message's ephemeral X25519 pubkey.  There is no
MAC: the outer structure is signed with the account key, so the value can only have been written by
a holder of the seed, who could equally have written any other.

## New device setup

A device that generates a brand new account creates its device group at once, with only itself as a
member.  (The stored data in this single device case is not particularly useful, but is needed to
allow other devices to link.)

Any other device outside a group -- one that has restored an account, or been removed from its
group -- checks namespace 21 for device group messages, and finds one of:

- **None at all.**  Either the account has never had a group, or it had one and every device was
  offline for longer than the group message TTL, so that it expired.  The two cannot be told apart
  from the swarm, and creating a group in the second case forks the account, so the device does not
  create one on its own.  The user decides between starting a new group and bringing an existing
  device online to link this one.
- **One or more groups it cannot read.**  It may ask to join one -- where there is more than one,
  the account has forked, and the most recently active is the natural choice -- or start a new
  group instead, which dissolves them (see "One group per account").

A device that can decrypt a group message is already in that group, and needs nothing further.

The rest of this section describes asking to join.

### Initiating a device link

A new "device link" message type is introduced, and will be stored in the account's (private)
message namespace 21.  This message is constructed as follows:

    {
        "id": "unique-client-identifier1",
        "info": {
            "type": "i",
            "timestamp": 1777777777,
            "seq": 1,
            "description": "iPhone OS 28 - Alice's phone",
            "version": 2025000,
            "unknown_extra_field": { "x": 123, "y": [1,3,997,"x"] },
            "device_pubkey_x25519": "abcdef123...",
            "device_pubkey_mlkem768": "...(1184 bytes)..."
        }
    }

That is, it is simply the information to add to the linked device list plus some metadata.  It is
uploaded to namespace 21 with a TTL of 10 minutes.  (Since device linking requires a user to have
access to both devices at the same time, a longer TTL accomplishes nothing.)  A device has one
request out at a time, and what it does while waiting on it is in "Confirmation on the requesting
device".

The request is encrypted to the group asked to join, using the `link_x25519` pubkey from that
group's messages, so that only the group's members can read it.  The device fetches namespace 21
just before asking and uses the newest of the group's messages that fetch finds, rather than
whatever it fetched last: a key the group has since rotated away from may be one it refuses
requests under (see below), and the fetch also shows whether the group is still there, and brings
in an admission on a request already out.  It must not be readable by every
holder of the root seed: a removed device still holds the seed, and a request it could read would
give it the requesting device's keys and SAS, enough to admit that device into a group of its own.
Encrypting to the group also means only that group's devices prompt for it, where an account has
more than one.

The encryption is that of one-to-one messages (see "One-to-one Message Encryption") without the
ML-KEM steps, there being no ML-KEM key to encapsulate to, and so not X-Wing.  With `X` the group's
`link_x25519` and `S` the account's long-term pubkey:

1. Generate an ephemeral X25519 keypair, e/E.

2. Compute the encrypted key indicator, which tells the group's devices which of their current and
   recent account keys the request was encrypted to:

       kiss = BLAKE2b_2(E || S, key=eS, pers="SessionDvGrpKISS")
       ki   = X[0:2] ⊕ kiss

   Without `kiss` the indicator would tell anyone who can see the group's messages, where `X`
   appears in the clear, which group and key a request was meant for.

3. Derive the key and nonce:

       kn = BLAKE2b_56(eX || E || X, pers="SessionDvGrpLink")
       k  = kn[0:32]
       n  = kn[32:56]

   BLAKE2b rather than the SHA3-256 and SHAKE256 of one-to-one messages: those follow from X-Wing,
   which this is not, and every other derivation in device groups is BLAKE2b.

4. The request dict above is signed with the account's Ed25519 key, under a `"~"` key appended to
   it in the same way as a one-to-one message's inner signature.  A request is not otherwise
   authenticated: without the signature, anyone able to see the group's `link_x25519` -- including
   a storage server -- could encrypt a request of their own to it, and have the group's devices
   prompt for a device that does not exist.

5. The signed request is encrypted with XChaCha20-Poly1305 using `k` and `n`, and the message is
   the bt-encoded dict:

       {
           "": "L",
           "E": "...ephemeral X25519 pubkey...",
           "L": "...encrypted request...",
           "i": "...ki, the 2-byte encrypted key indicator..."
       }

A member decrypts with `xE` for the account key whose X25519 pubkey begins with `ki ⊕ kiss`,
`kiss` being computed as `BLAKE2b_2(E || S, key=sE, ...)` from the account's long-term secret `s`.

That may be any key the member still holds, current or retained, since the group may have rotated
since the requesting device read its link key -- except a key that also reached a device no longer
in the group.  A removed or departed device keeps every account key it was given, and any holder of
the seed can publish a group message: one carrying the real group's identifier with such a key as
its `link_x25519` has a joining device encrypt its request to a key that device can read, so that
it can admit the joining device into a group of its own while the real group prompts for the same
request -- showing the user the very emoji they then confirm.  A member refusing such requests
leaves that device's admission the only one, with nothing on the user's devices to confirm it
against (see "Confirmation on the requesting device").

To tell those keys apart, a member records, for each account key, the devices it was delivered
to: a payload is encrypted to exactly the live records it carries, so every payload carrying a
key, whether the member merged it or pushed it, delivered the key to each of them.  That set is
exactly the keys a removed device holds, the retained keys handed over on its admission included,
and every other retained key is honoured, so an ordinary rotation never costs a request its
prompt.  What it does cost is a request made under a key that reached a device removed in the
meantime, which lapses unprompted and has to be made again; with the requesting device fetching
the group just before it asks, that takes a removal within moments of the request.

#### Handshake short authentication string

This initial key also implies a human-readable short authentication string that allows a user to
verify that the request being accepted on a linked device matches the one that originated on the new
device.  This authentication string is an emoji sequence selected from a set of 64 distinct emoji
values as specified in the Matrix specification's short authentication string emoji list (see
https://spec.matrix.org/v1.17/client-server-api/#sas-method-emoji), in that list's order.  Clients
shall show the first 7 of these emoji, with an optional "extended" view (either a toggle, or visual
indicator) to show an extended version of the SAS with 14 additional emoji (21 total) that users
can use for extra assurance.  As the Matrix specification has it, clients SHOULD show each emoji
with its description: the English name the list gives it, or a translation of that name.  What the
user checks is that the two devices show the same emoji, not identical glyphs: a few look alike, or
render differently, from one platform to another, and the descriptions settle which is which.

The exact sequence is calculated from a list of 6-bit (0-63) integer values that determine the index
of the emoji value, generated as follows:

- seed = Argon2id(M, salt=blake2b(M, size=16, pers="SessionLinkEmoji"), size=16, cost=64MiB, ops=2)
  where M is the signed request dict, as decrypted from `L`.
- emoji indices are then selected by interpreting the resulting 16 bytes as a 128-bit, little-endian
  encoded integer where index 0 is the value of the least significant 6 bits, index 1 is bits 6-11,
  and so on.
- the final secret displayed on both devices is then the first 7 emoji, each with its description.
  When displaying an extended version, devices are recommended to format as 3 lines of 7.

Each side derives the seed from the request itself, when it makes or receives it, so a change to
these parameters affects only requests in flight across it, whose two sides then show different
emoji and are simply asked again.

This short string simply serves as a quick visual representation of the device key.  This prevents a
rogue device with the root Session key from being able to wait for and quickly replace a device
linking message with its own version with a replaced key to masquerade as a different device joining
a device group: such an attacker would immediately alert the user because of the different SAS key.

We use a memory-hard Argon2id hash here to make collisions costly: if a device with compromised root
keys (but not device group keys) wanted to gain entry into the device group, it would have to notice
the linking request in the swarm and quickly replace it with its own linking request to fool the
user into accepting *it* rather than the intended device.  Given that the 7 emoji sequence offers
only 42 bits of entropy, a cheap hash here (such as BLAKE2b) could conceivably be collided within
the short window before the user accepts the request; a memory-hard hash makes that infeasible.
64 MiB and 2 passes cost each device a few tens of milliseconds, once per request; a collision
attempt pays that for every one of its ~2^42 tries.

### Device link request handling

Upon receiving a device link request in namespace 21 that it can decrypt and whose signature is
valid, an existing (linked) device must display to the user a screen with the new device details,
asking for confirmation of the new linked device.  This information should generally consist of the
device type, description, and version, time the request was made, and the short authentication
string.

In some circumstances, additional information might also need to be confirmed or requested:

- if the new device has the same device identifier as an existing device then the user should be
  told that accepting this will replace the existing device in the device group.  (This path is
  relatively rare, but would apply, for instance, if someone restores their system from a backup
  with expired keys that needs to re-join the device group with new keys.)  Only a request made
  after the record it would replace counts: an older one is the request that first admitted the
  device, or one since superseded, fetched late.  A device identifier the group holds a removal or
  departure for is spent, and a request under it is ignored.

- if there are no available additional linked device slots (i.e. because the user is not a Pro user,
  and has used all available non-Pro device slots) then the user must be informed and given a list
  of existing devices to kick out of the device group.  The *current* device, if shown at all,
  should not be selectable in this list.

The user is then given a choice to accept or deny the linking request.

#### Device link request denial

If the user chooses to ignore the request then by default the device simply stops prompting for it,
and takes no other action: another of the account's devices can still accept the same request.

Ignoring may optionally also delete the request from the namespace, so that no device can accept
it.  This is for a request the user does not recognise, rather than one that is merely being
answered elsewhere.

#### Device link request acceptance

Upon accepting a device linking request, the existing linked device accepting the new device must:

- update the linked device configuration with the new device details
- regenerate the new linked device encryption with the new details, and newly encrypted for the new
  device.
- push the updated linked device config to the account's swarm.

Accepting a request that replaces an existing device puts the requested record in place of the one
held, with a seqno above both that record's and the request's, so that it wins the merge on every
device -- the requesting device's own included, which may have lost track of its seqno along with
its membership.  The accepting device also rotates the account key: a copy of the device as it was
still holds the replaced record's keys, and must not read what comes after.  A device that saw the
request without answering it treats it as accepted once a group message gives the device the keys
the request asked for.

The device that requested linking, meanwhile, continues to monitor namespace 21 for an updated
device message that it is successfully able to decrypt.

#### Confirmation on the requesting device

Decrypting a group message is not by itself enough for the requesting device to consider itself
linked: its user must also confirm on it that its SAS matches the one the accepting device showed.
The two happen strictly in that order.  While its request is out, the requesting device shows its
SAS and the request's deadline, and has nothing to confirm.  Once a group message admitting it
arrives it is **approved**: it holds that message, and asks its user whether the SAS matches what
the accepting device showed.  The user's confirmation then admits it.  A confirmation before the
approval is refused: given ahead of time, it would authorise whatever admission came next, which is
what it is there to prevent.

Encrypting the request to the group stops a removed device, or any other seed holder outside the
group, from reading it.  It does not stop one from publishing a group message of its own, carrying
its own `link_x25519` and even the real group's identifier.  A device that encrypts its request to
such a key has its request read by that impostor, which can then admit it to a group of its own --
and from the requesting device, that is indistinguishable from being accepted.  The real group
cannot read such a request at all, and so never prompts for it.  Asking the user to confirm on the
requesting device closes this: the user confirms only having seen the same SAS on one of their own
devices, which happens only if the request reached the real group.

The confirmation belongs to one request, so an admission is matched to the request it accepted: the
record it admits is the one that request carried, identified by its timestamp and X25519 key.  A
device stamps each of its requests later than the one before, so no two carry the same record.  It
keeps its requests for as long as an admission accepting one could still be in the swarm, and:

- an admission matching none of them is ignored: the device asked for nothing that it answers;
- one matching the device's newest request is held until the user confirms it -- even past that
  request's deadline, since the acceptance came in time and only the message carrying it arrived
  late.  Once one is held, the request no longer lapses, and any other admission on it is ignored:
  the user may already be comparing emoji against the first, and a seed holder could otherwise
  swap an admission of its own in beneath their confirmation;
- one matching an older request is ignored.  The user has moved on to a newer request, whose SAS is
  what they are now looking at, and that one admits them instead.

There is no cancelling a request.  It lives in the swarm until its deadline, whatever the requesting
device shows meanwhile, and the device asking again for the same group while it does -- approved or
not -- reopens that request, with the same SAS and deadline, rather than making a new one, which
would show its user new emoji while another device may be approving the old ones.  Only a request
that lapsed unapproved, or one for another group, is replaced by asking again.

## One group per account

An account has one device group.  Two cannot both work: each rotates the account key and publishes
its own to namespace -21 (see "Account keys"), each publish replacing the other's, so at any moment
roughly half of the account's contacts would be encrypting to a key that only some of its devices
hold.

A second group can still come about: a device restored from the recovery phrase starts a group of
its own when it should have joined the existing one, or every device of a group is away for longer
than its messages last, and comes back to find another.  No device settles this by itself.  The user
does, by choosing one group, which **dissolves** the others, and always from a position of
knowledge: on a device that can see what it is choosing between.  Dissolving is only ever the effect
of that choice, and a device dissolves groups in exactly these cases:

1. **Starting a group.**  A device that starts one is choosing its new group over every group in
   view, and dissolves them all -- its own included, when it starts from inside a group -- but
   only the groups its user confirmed replacing: if another has come into view since the user was
   shown them, starting is refused and nothing is dissolved, for the user to be asked again.
   Starting over is the one step: there is nothing to leave first, since the group it was in is
   dissolved with the rest.  It dissolves its own as a sole member leaving does, deleting the
   messages it merged and naming the group in the tombstone, and takes a new device ID, so that
   the devices still in that group learn from the tombstone that it is gone.
2. **Completing a join while others are in view.**  A device that sees more than one group and asks
   to join one is choosing it over the rest, and once it is admitted -- the user having confirmed
   the SAS -- it dissolves them.
3. **Keeping its own group when forked** (see "Forks"), over the other group in view.
4. **Republishing a tombstone it has already seen**, when a group it knows to be dissolved pushes
   again (see "Dissolving a group").  This decides nothing: the choice was made when the group was
   first dissolved.

A device never dissolves a group of its own accord.  One that comes back to an empty swarm pushes
its group again, its account key being due for rotation if nothing else; one that comes back to
find its own group's messages gone and another group live is dropped (see "Forks"), and a dropped
device never dissolves anything new.  So no two devices can dissolve each other by accident, and
nothing has to decide which of two groups came first.

### Forks

A device in a group whose messages are in the swarm, that sees a message carrying another group's
identifier while no tombstone names its own group, is **forked**.  Nothing has been decided, and
nothing is wrong with its group, which goes on working -- pushing as it would anyway -- while the
user decides, on this device or another.  It asks its user, showing when the other group was last
active -- the `time` of its newest message -- which tells a live set of devices ("an hour ago")
from a stale leftover ("two months ago").  The user keeps this group, dissolving the other, or
leaves it for the other: leaving it (see "Leaving a group") and asking to join the other, as any
device outside a group does.  Or the user starts over from this device, dissolving both.

A device in a group whose messages are gone from the swarm, while another group's are there, is
**dropped**: no longer in a device group, and unable to tell why.  Its group's messages leave the
swarm only by expiring, which takes every device of the group being offline for the whole TTL, or
by a seed holder deleting them: it was removed or replaced while away and its group moved on, it was
away too long, or its group was dissolved and the tombstone saying so expired before it came back.
Whichever it was, the account's group is now the other.  A dropped device pushes nothing, which
would bring its group back beside that one, and decides nothing about the other group: it never
dissolves anything new.  It comes back as a new device, under a new ID, by asking to join, or by
starting a group -- which, like any start with groups in view, dissolves them.  A device is dropped
too by a message from its group that it cannot read and that cannot tell it why (see "Displaced
devices").

A device outside any group that sees more than one may join any of them, the most recently active
being the natural choice; the rest are dissolved once the join completes.

### Dissolving a group

A group is dissolved by deleting its messages from the swarm, which any holder of the account seed
can do, and publishing a **tombstone** naming it, so that the group's devices learn of it within a
fetch.  It is resolution rather than permission: anyone with the seed could delete the messages
without saying so.

A group's sole member leaving it dissolves it too, with a tombstone like any other (see "Leaving a
group"): a group nobody is in is one no device of another group should go on counting as a fork.

The tombstone is a bt-encoded dict in namespace 21:

    {
        "": "T",
        "@": "...the dissolved groups' identifiers, encrypted...",
        "A": "...ephemeral X25519 pubkey...",
        "t": 1777777777123,
        "~": "...above data signed with the long-term account key..."
    }

`@` is the 8-byte identifiers of the groups dissolved, one or more, concatenated and encrypted as
one XChaCha20 stream with the key and nonce a group message's identifier uses (see "Group
identifier"), from this message's own `A`.  The first is therefore encrypted exactly as a lone
identifier would be; any seed holder can read them, and to anyone else they differ from one
tombstone to the next.  `A` is generated for the tombstone and its secret half discarded, since
nothing is encrypted to anyone: there is no payload and there are no recipients.  `t` is the time
the tombstone was written, as in a group message (see "Device data encryption"), with the same limit
on how far ahead of the reader's clock it may be.

The tombstone is transient.  It is stored with the group messages' 30-day TTL and never renewed,
and a group push never deletes it.  Its only job is to reach the dissolved group's devices that are
online in the meantime; one offline for longer finds no message of its group at all.

A device reading a tombstone that names its own group has been **dissolved** out of it.  This is a
different state from being forked: here the decision has been made, by the user on another device.
The device stops acting for the group, forgets everything of it -- its devices, its messages and its
account keys -- and takes a new device ID, since nothing remains that the old one is any use for.
It may then ask to join the group that was kept, as any device outside a group does.  Its messages,
the account's configs and the groups it has seen are kept, as for a removed device.  A tombstone
naming any other group only stops the device counting that group among those in the swarm.

Every device remembers each identifier a tombstone names, with the tombstone's `t` (the newest,
where several name it), and keeps that memory whatever group it goes on to, except that a device
admitted to a group forgets any dissolution of that group it had heard of: joining it was the
user's later choice.  That memory, a few bytes a group, is what keeps a dissolved group dissolved
without tombstones having to stay in the swarm forever.  A message carrying a dissolved identifier
that was written before the dissolution is only a leftover that the dissolving device did not know
of: a device in a group deletes it from the swarm, and every device ignores it.  One written after
it is a **revival**: a device of that group that never heard of the dissolution, back after the
tombstone expired, has pushed again.  A device in a group, forked or dropped as it may be, deletes
it and publishes a new tombstone naming the group, and the device that pushed rejoins the group
that was kept; in the time between, contacts may have encrypted to its group's account key, which
cannot be helped.  A device outside any group is in no position to say which group is the
account's: it takes a group that has pushed since as it would any other.

A remembered dissolution is never stale.  A device that sees a group again after a tombstone named
it is always looking at a revival by devices that missed the tombstone, never at a group the user
has chosen since, because a revived group and a live kept group cannot coexist.  A device of the
dissolved group that comes back while the kept group is in the swarm finds its own group gone and
another live, and is dropped, which pushes nothing; so the dissolved group can come back only into a
swarm the kept group has lapsed from, and any member of the kept group that returns dissolves it
again before anything else.

### Leaving a group

A device leaves its group when its data is about to be cleared, so that the group does not go on
counting and encrypting to a device that is gone, and when its user, forked, chooses the other
group.  A device in a group cannot ask to join another: an account has only one group, so there is
no moving from one to another.  It leaves its group first, and then asks as any device outside a
group does.

Leaving a group, for whatever reason -- leaving it as above, being removed, displaced or dropped
from it and then asking to join or starting a group, having it dissolved -- always means a new
device ID, with new device keys.  A record of the device in a group it left can then never meet one
under its new ID, in that group or any other, so its next record starts again at `seq` 1 with
nothing held for it, and coming back to the group it left is asking to join as a new device: the old
ID is spent there, as a departed one.

Only a member in good standing tells its group that it is leaving.  A removed device's departure
could not lower its removal, a displaced device's would be taken as the departure of whichever
device now holds its ID, and a dropped device's would bring back a group gone from the swarm, or
come from a device that may have been displaced; a device removed, displaced, dropped or dissolved
only forgets its group.  A member in good standing leaving its group:

- If it was the group's only member, dissolves the group (see "Dissolving a group"): deletes its
  messages from the swarm and publishes a tombstone naming it, and remembers it as dissolved.  No
  device is left to read the messages, and deleting them alone is not enough: a deletion is
  invisible, so the devices of any other group on the account would go on seeing this one as a fork
  until it lapsed, 30 days on, and none of them would dissolve it once the leaving device had joined
  their group, since it no longer knows of the group to dissolve.  Remembering it means a stale copy
  turning up later is dissolved again, by this device as a member of whatever group it joins next.
  The tombstone is harmless to the device itself: by the time it could read it back, it has
  forgotten the group, and only remembers the group as dissolved.
- Otherwise pushes one last update to the group with a departure tombstone for itself, so that the
  remaining members stop encrypting to it.  Being a departure rather than a removal, it does not
  appear in the `kicked` list.

The device builds that push under its old ID and stores it as a complete upload -- the message to
store, if any, with the hashes it deletes -- in the same commit that forgets the group and takes the
new ID, so that no interruption leaves one without the other.  It keeps the push until the swarm
confirms it: sent at once if it can be, and again after each fetch until it has gone, including
after a restart.  Nothing about sending it needs the group the device has since forgotten.  One
older than a group message lives is dropped unsent, since by then the messages of the group it was
for have expired anyway.  A tombstone dissolving a group (see "Dissolving a group") is kept and
sent the same way.

Either way it leaves all of the group behind -- its devices, its messages, and its account keys --
and a group it joins next brings its own, all of which arrive with the message admitting it.  A
group's account keys never carry into another: they would be handed to the new group's members in
every message the device pushed, and the newest of them could displace the new group's current key.
For the same reason a device starting a group starts it with a newly generated account key,
whatever it held before.

The departed device still holds every account key the old group had, and the group must move to one
it does not.  A removal does this in the same step: the removing device generates a new account key
and pushes it in the message that carries the tombstone, which the removed device is not given a key
to.  A departing device cannot do the same for itself, since it would know any key it generated,
and so the rotation is a second step: a remaining member that learns of the departure finds the
current key delivered to a device no longer in the group, and replaces it within the rotation
jitter (see "Rotating early").  The first to do so stands the others down; any that cross settle
as all crossing rotations do, the merge keeping the most recently created key as current and the
lowest seed breaking a tie.

# Account keys

Account public keys consist of a pair of public keys: an ML-KEM-768 pubkey, and a X25519 pubkey.  We
effectively follow the fundamentals of the draft X-Wing construction, but with some small
modifications as needed for the specifics of Session message construction.

The secret halves live only on the account's devices, shared through the device group and never
derived from the account seed.  Losing every device that holds them loses everything encrypted to
them, and restoring the account from its recovery phrase cannot bring that back.

Account public keys are stored in an account's namespace -21, which is a public "outbox" that only
the account owner can upload to, and anyone can fetch from.  This mechanism is used by other clients
to retrieve the public keys necessary to contact a user.

The message in this outbox consists of a bt-encoded dict containing:

- `"M"` -- ML-KEM-768 pubkey (1184 bytes).
- `"X"` -- X25519 pubkey (32 bytes).
- `"~"` -- "positive alternative" Ed25519 signature over the previous values in the dict (64 bytes).

Additional keys are ignored (they could be used by future versions to provide additional account key
data).

Clients should upload the message with a maximum (currently 30-day) lifetime so that even if all of
a client's devices are offline for an extended period, the keys remain available for other clients
attempting to contact them.  (Account keys would not rotate with such an extended outage of all
account devices, but this is preferred to falling back to the long-term key).

Clients look this outbox up when sending to a contact, and cache what they find.  A contact's cache
entry holds the keys last found, if any; `confirmed_at`, the last time a lookup said those keys are
current; and `cache_expiry`, when the next lookup is due.  Every outcome of a lookup does no more than
set these:

- **Within `cache_expiry`**, a send uses what the entry says, with no lookup: its keys for a PFS+PQ
  message, or with none, a message as described in "Non-PFS fallback" below.
- **Past it**, or with no entry, a send looks the keys up first and waits for the outcome:
  - *Keys found:* they are stored, `confirmed_at = now` and `cache_expiry = now + 6h`, and the
    message is encrypted to them.
  - *Nothing found:* if the entry holds keys confirmed within the last 29 days, they are still the
    account's, as below: `confirmed_at = now`, `cache_expiry = now + 1h`, and they are used.
    Otherwise any keys are dropped, `cache_expiry = now + 1h`, and the message is sent non-PFS.
  - *The lookup failed:* if the entry holds keys confirmed within the last 24h,
    `cache_expiry = now + 1m` and they are used.  The minute keeps a burst of sends from making a
    lookup each while still trying again soon, and since `confirmed_at` is untouched the fallback
    runs out 24h after the last confirmation.  Otherwise the message is not sent: a client that
    cannot reach the contact's swarm to look the keys up cannot deposit a message there either.  It
    waits, and the lookup is retried with a backoff (10s, doubling to 5 minutes) until one succeeds
    or finds nothing.

The 6h refresh bounds how long contacts go on sending to a key the account can no longer read.  An
account restored onto a new device group starts with a new account key when its old keys were only on
devices that were lost, and every message encrypted to the old key until a contact looks again is
unreadable.  Clients should look up ahead of the send, when the user starts writing to the contact,
so that a send is not held up; a client with no such moment, such as a bot, looks up immediately
before the send, over the connection it opens to deposit the message anyway.

Finding nothing does not mean a held key is gone.  The outbox message lives for 30 days and a
rotation publishes a replacement, so an empty answer means nothing was published in the last 30
days: the account has not rotated since then, and a key confirmed within that window is still its
current one.  Its devices have only been offline too long to republish it.  The 29 days are that TTL
less a day, as margin for clocks and for the swarm's expiry.  Each such answer re-confirms the key,
so a client that looks at least every 29 days goes on using it however long the account stays
offline, which is correct: no rotation can have happened unseen.

There is deliberately no hard expiry on a held key.  An account whose devices are all offline does
not rotate, so an old key is still the current one, and the only alternative is the non-PFS
encryption, whose key never rotates at all.  Non-PFS is for a sender holding no key it can still
use: the account never published one, or the sender confirmed the one it holds more than 29 days
before a lookup that found nothing.

An entry with no keys within its `cache_expiry` is the record of a lookup that found nothing.
Without it, every message to an account that has not published keys would incur a fresh (and
futile) network round trip.

This signed key payload should be rotated periodically by any of the clients; how rotation works
specifically is discussed later.

When validating the key payload signature, the client converts the recipient's long-term account key
(which is an X25519 pubkey) into the positive alternative Ed25519 of the two possible associated
Ed25519 pubkeys, and verifies the previous values in the message using that pubkey.

(To elaborate on this positive alternative signature, which used in some existing Session code for
signature verification: because the recipient only knows the session ID -- which is an X25519
pubkey, converted from the true Ed25519 pubkey of the client -- the recipient can recover the
underlying Ed25519 pubkey *except for its sign*.  The tweaked signature mechanism accounts for this
if the actual pubkey is negative by using the negative value of the Ed25519 private scalar to
compose the signature, which results in an Ed25519 signature verifiable with the positive
alternative of the two possible pubkeys that result from converting the session ID X25519 pubkey
back to an Ed25519 pubkey.  This "assume positive" approach is the same as that used in Signal's
XEd25519, but unlike XEd25519's random nonce use, retains Ed25519's use of the seed as keying
material, thus maintaining Ed25519's fully deterministic signature generation.)

## One-to-one Message Encryption

Encryption keys used to encrypt DMs, given a set of published ML-KEM-768 and X25519 pubkeys, is
constructed as follows:

0. If the contact's cache entry is past its `cache_expiry` (see "Account keys" above), the contact's
   keys are looked up first.  Clients should generally do this preemptively, such as when the user
   starts writing to the contact, to avoid the extra lookup latency when actually sending a message.

   This provides the recipient's current account pubkeys, M (ML-KEM-768) and X (X25519).

1. Generate an ephemeral X25519 keypair: e/E.

2. Using the recipients *long term pubkey* S (i.e. Session ID without the 05 prefix) compute a "key
   indicator shared secret":

       kiss = BLAKE2b(E || S, key=eS, personalization="Session-Msg-KISS", length=2)

   (Do not be alarmed at the long term key (S) usage here: this is only used for a tiny bit of
   metadata obfuscation in the outer encoding, but *not* for the actual message encryption).

3. Compute an encrypted key indicator by taking the first two bytes of the ML-KEM-768 pubkey and
   XORing these with the two bytes of the `kiss`:

       ki = M[0:2] ⊕ kiss

   (This encrypted value is an important optimization that allows the recipient to identify *which*
   of its current and recent keys was used -- without it, it would have to trial decrypt using many
   different keys, which would be annoyingly expensive, particularly when processing many incoming
   messages when coming online after an extended offline period.  While this key indicator could be
   provided plaintext as plaintext without compromising message security, doing so would leak some
   metadata about the message sender: because not all senders refresh the remote's pubkeys at the
   same time, repeated messages from "early" refreshes and from "late" refreshes would be
   correlatable through their selected index.  By using basic encryption with the long term key for
   this index, to anyone without the recipient's long term key, no correlation can be drawn among
   senders based on key refresh times).

   Note that we do *not* use a MAC or AEAD here, and thus do not detect tampering with this key
   index.  This is deliberate: any tampering with the key *will* still result in failure because it
   will either indicate a key that does not exist (failing decryption), or it will point to the
   wrong key, which will also fail decryption (because of the encrypted message's AEAD).

4. Generate an ML-KEM-768 encapsulated shared secret and ciphertext:

       ssₘ, ciphertext = Encapsulate(M)

5. Generate an X25519 shared secret from the ephemeral and recipient account keys (*not* the
   long-term key):

       ssₓ = eX

6. The message encryption key is constructed by using "X-Wing" key derivation mechanism (which is
   basically just a hashed combination of X25519 and MLKEM shared secrets) to generate the X-Wing
   shared secret:

       ss = SHA3-256(ssₘ || ssₓ || E || X || '\.//^\')

   (Note that the cryptography here is exactly that of X-Wing, however it must calculated separately
   rather than use a single library X-Wing calculation because we also use the ephemeral X25519
   private key `e` back in step 2 for the key indicator; in normal X-Wing implementations this key
   is not exposed).

   This is then fed into SHAKE256("SessionV2MessageSS" || ss) and "squeezed" to produce a 32-byte
   key, `k`, and 24-byte nonce, `n`, which are used below to encrypt the message body.

7. The overall inner plaintext message is constructed using a bt-encoded dictionary containing:

   - `"S"` -- the sender's Ed25519 pubkey (32 bytes).  *Not* the session ID, but the session ID can
     be easily derived from it.
   - `"c"` -- the message content.  This is the encoded `Content` protobuf data
   - `"~"` -- Ed25519 signature, verifiable with S; this signs the value:
         BLAKE2b(..., size=64, key=recipient_sessionid_33B, pers="SessionV2Message")
     where "..." is the entire bt-encoded content (which may contain other, unknown keys) up to but
     not including the `"~"` key.  (This is oxenc's standard append_signature/consume_signature API).
   - `"~P"` -- optional Session Pro Ed25519 signature.  If this message uses Session Pro features
     then this is the signature verifying that the sender is a valid Session Pro account.  (The
     public key itself is contained within the protobuf, and so when parsing, this value is merely
     extracted but verification is deferred).  Like ~, this signature is over everything before it
     in the encoded dict (include the ~ signature).

   This value is tail-padded with null (0x00) bytes such that:
   - the post-encryption size (see step 9) is a multiple of 256 bytes.
   - the padded message size is always at least 256 bytes.  (When combined with the previous rule,
     this means the minimum padded message size is 396 bytes, with the current encryption data
     adding 1140 bytes).

8. The value is encrypted using XChaCha20+poly1305 encryption using key `k` and nonce `n` from step
   6.

9. The encrypted value then written as a concatenation of:

   - `0x00 0x02` -- two bytes that identify the message as a Session v2 message.  The 0x00 in
     particular is needed to unambiguously identify it as *not* a protobuf message (Session v1
     messages are protobuf-encoded on top of the encryption layer).  Values other than 0x02 and 0x01
     (used for non-PFS fallback, discussed below) are reserved for future use.
   - `ki` -- two byte encrypted key indicator from step 3
   - E -- 32-byte ephemeral X25519 pubkey
   - ciphertext -- 1088-byte ML-KEM-768 ciphertext
   - encrypted value from step 8.

   and so, with padding applied, all messages should have sizes of the sum of:
   - 2 -- message prefix
   - 2 -- key indicator
   - 32 -- ephemeral X25519 pubkey
   - 1088 -- MLKEM ciphertext
   - 16-byte -- poly1305 MAC, inside the encrypted payload.
   - 396 + 256×N, N >= 0 -- padded message size

   that is, 1536 + 256×N (e.g. 1536 minimum, but expandable in increments of 256 bytes).

### Our own copy of a sent message

A one-to-one message is sent twice: to the recipient, and to the sender's own swarm so that the
sender's other devices see it, that copy's DataMessage carrying `syncTarget` to say whose
conversation it belongs to.  Each copy is encrypted for its own destination, so the copy in our own
swarm says nothing of how the recipient's was encrypted.  It carries that instead as
`DataMessage.syncEncryption` (field 1000): 1 for v1, 2 for v2 without PFS (the fallback), 3 for v2
with PFS+PQ.  It is set only on that copy, never on the recipient's, and only once the recipient's
copy has been encrypted -- which can wait on fetching the recipient's keys -- so the copy for our
own swarm is sent after the recipient's is encrypted, not beside it.  A copy without the field (one
whose recipient's copy was never encrypted, or from a client that does not set it) leaves the other
devices not knowing, and an unknown value is ignored.

## Account Key Rotation

Clients rotate the account keys, shared by all devices, 12h+ε after the current one was created.  ε
here is a delay within a 2h window (the rotation jitter, shared with device keys: see "Device key
rotation"), between -1h and 1h, calculated differently for each device, to reduce the possibility
of collisions and to obscure the exact device timings of key publishing.  Details of ε selection
are discussed below.

Only a member of a device group in good standing rotates, and only once a fetch of namespace 21 has
been merged: a device checks what is due after each fetch.  A device back from a long absence
therefore finds its rotation overdue and rotates once, after its first fetch -- not before, since
what waited for it in the swarm was encrypted to the keys it had.  A device whose swarm is quiet,
and so might not fetch for a while, fetches when its next rotation falls due.  A device outside a
group, or removed, displaced, dropped or dissolved from one, rotates nothing on schedule.  A device
due both an account key and a device key rotation makes both before the one push that carries
them.

An account key itself is a single 32-byte seed value that is expanded into 96 bytes using
SHAKE256("SessionAccountKeys" || seed) to produce:

    - 32B X25519 private key
    - 64B MLKEM-768 seed

To perform a rotation, the device generates a new secure random 32-byte seed and updates the existing
seed (if any) to be marked as rotated away at the current timestamp.  Any old keys that have been
rotated away for more than 16 days are discarded.

The list of all account seeds is then added to the "account_keys" section of the device group
payload, including the creation and rotation timestamps (to synchronize with other devices).

This updated device group payload is then re-encrypted for current devices and pushed to the swarm.
Simultaneously, in the same request, the rotating client also pushes the new account public key to
namespace -21, as described above -- once the account has enabled PFS/PQ (see "Migration"), and
not before: publishing the key is what has contacts start sending PFS/PQ messages.

Publishing is otherwise the same as rotating: only a member of a device group in good standing does
it, and only once a fetch of namespace 21 has been merged.  A member whose current key it has not
seen on -21 -- neither confirmed by its own store nor fetched back from there -- publishes it after
its next fetch, on its own if nothing else is owed; so enabling PFS/PQ publishes the current key at
once, without waiting for a rotation.  A store that fails is retried as a failed group push is.

### Account Key Rotation timer

In order to determine when a device should initiate key rotation on behalf of the device group, a
random delay is deterministically calculated by each device based on the current active account
seed and when the current seed became active:

    t = t_prev + 12h + ε
    ε = -1h + 2h × (1 - u^N)

where t_prev is the unix timestamp when the current seed was created, and t is the target timestamp
for the current device.  `u` here is a device-specific quasi-random value distributed as Unif[0, 1],
and N is the number of account devices.

`u` itself can be computed in any way so long as it changes with the current seed and device id, but
we suggest the following (and this is used in libsession-util):

- the seed is computed as BLAKE2b(deviceid, key=current_seed, pers="SessionAccKeyRot", size=8)
- that seed is interpreted as a little-endian, 64-bit unsigned integer
- that integer is then converted to double and divided by 0x1p64 (that is: the double value 2^64)
- the resulting value is the `u` value for the calculation of ε

This then provides a consistent `t` value for any given device for any current seed value.  That
value is a unix timestamp: the device should rotate when the timestamp is reached (or exceeded).

This construction is specifically designed to statistically mask the number of devices in an
account: with N active devices, the distribution of the *smallest* ε value (which is when the
effective account key rotation occurs, assuming all devices are online) over the N devices works out
to `Unif[11h, 13h]`, which is exactly the same as the uniform distribution of a single active
device.  That masks the count from the timing of rotations only: the swarm can still estimate it
from how often the account's devices push and poll, and roughly from the `keys` bucket each group
message carries.

This distribution is also designed to break up the rotation times to reduce the occurences of
conflicting updates (which then have to be resolved) versus having all devices try rotating at the
same time.

Note that Storage Server public outbox namespaces can only hold one message at a time: uploading a
new message replaces an existing one (if present), and so clients will only see one at a time.  It
*is*, however, possible for two devices in a group to race to upload a new key, and so any such
rotation attempt must preserve *both* keys to account for the brief window where some client may
have fetched the quickly replaced key.

Account keys in general must be preserved (in the device group config) for 16 days *after* they
have been rotated away so that an offline device is able to decrypt any incoming messages that may
still be in the swarm: the 1-to-1 message max TTL of 14 days, plus how long a sender may go on
encrypting to a key after it is replaced -- normally under the 6h refresh, but up to 24h for a
sender whose lookups keep failing (see "Account keys") -- plus 24h of margin for clock skew and
late storage.

### Rotating early

An account key can be replaced before its time, though not retired: contacts go on using it until
they next look (within 6h, or up to 24h for one whose lookups fail) and every device keeps it for 16
days after it is rotated away.  Replacing it early buys one
thing, that link requests stop being honoured under it (see "Initiating a device link"), and is done
for one reason: **the current account key was delivered to a device that is no longer a member**.

A device knows which: for each account key it keeps the devices it was delivered to, since every
payload carrying a key is encrypted to exactly the live records it carries.  When the current key
was delivered to a device now removed or departed, the device's next rotation is due at once if it
removed that device itself, and otherwise at `now + uniform[0, 2h]` -- picked when it first sees
this, and kept, so that it holds still across fetches and restarts.  Only the remover knows it is
one, from a mark it keeps on the removal, so its zero delay collides with nobody's; two devices
removing the same device at once both rotate at once, an ordinary tie that the merge settles.

The rule is a fact about the key rather than about timing, and covers:

- **A removal.**  The remover rotates as part of removing, so the condition is ordinarily false
  everywhere from the start.  It matters when a member that had not heard of the removal rotates
  meanwhile and delivers its new key, newer and so current everywhere, to the removed device: the
  remover then replaces it at once, and every other member within the jitter.
- **A departure.**  The departing device holds the current key and cannot rotate it away for
  itself, so every member learning of the departure is due within the jitter.

Standing down needs nothing of its own: the first replacement's payload lists the device as gone,
so the key it carries was never delivered to it, and the condition is false on every device that
merges it.  A device admitted to a group is not caught out by departures in the group's history
either: the key its admission gives it was delivered only to the live devices that admission lists.

Accepting a request that replaces a device's record rotates at once too (see "Device link request
acceptance"): the displaced copy holds the current key under an ID that is still a member, which the
rule cannot see.

Every device keeps and honours an early-replaced key for contacts' messages for its full retention;
only link requests refuse it.  A removal also brings device keys forward (see "Device key
rotation").

## Device key rotation

Each device's own device keys (`device_pubkey_x25519` and `_mlkem768`, see "Inner device data")
rotate on the account keys' 12h period: at `created + 12h + δ`, `δ` uniform in [-1h, +1h] -- the
same 2h jitter, without the skew, since a device's keys are its own -- picked when the keys are
made.  As for account keys, only a member in good standing rotates, and only after a fetch, both in
one push when both are due; a device asking to join keeps the keys its request names until it is
admitted.

A device keeps only its current device keys and the ones before them.  That is enough: a device
pushing a group message fetches first, and so encrypts to each member's newest published keys,
while the previous ones cover a rotation that lands between another device's fetch and its push.
What only an older key could decrypt is a superseded snapshot or a forgery.

Rotation is also what makes a former member's knowledge of the group go stale.  A removed device
keeps the device pubkeys it saw, and holding the seed, could encrypt a forged group message --
adding a device of its own, say -- to them; once those devices have rotated, nothing it encrypts
is readable by any of them.  So on learning of a removal, a member brings its next device key
rotation forward to `now + uniform[0, 2h]`, unless it is due sooner already, and what the removed
device knows goes stale within the jitter.  Devices offline throughout stay exposed until they come
back and rotate.


# Non-PFS fallback (post transition)

When a client seeks to contact another Session account for which it holds no PFS+PQ keys it can use
(see "Account keys": the account has not published any, or the client's lookup found none and the
key it held was confirmed too long ago to trust, or what was published could not be parsed), the
client sends a message using the receiver's long term key.  A lookup that *failed* is not such a
case: the message waits for one that succeeds, unless a recently confirmed key can be used.

During the transition period, these messages are backwards compatible "v1" direct messages (see
the Transition Period section below) as the client may be communicating with a client that has not
yet upgraded to support the Session v2 PFS+PQ key encryption.

Once the transition period is over, clients start sending using a new v2-like message format,
so as to shed the legacy encoding of the current v1 message format.

Such a message is encoded identically to be externally indistinguishable from a PFS+PQ v2 message,
by using random values for `ki` and `ciphertext`.

The actual encryption keys used are entirely different (since there is no actual PFS or PQ keys to
be used): for a recipient Session ID `S`, where `R` is the X25519 pubkey of that session ID (i.e.
the key with the 05 stripped off), the encryption keys are generated using a random ephemeral X25519
keypair (e, E) as:

    ssᵣ = eR        // = rE, when computed by the recipient
    ss = SHA3-256(ssᵣ || R || E || 'SessionV2NonPFS')
    x = SHAKE256("SessionV2NonPFSSS" || ss)
    k, n = 32 and 24-byte "squeezes" of x

(The key construction here deliberately mirrors the encryption used for PFS+PQ messages, but adapted
for use with X25519 keys using only the long-term keypair).

The `k` and `n` here are the key and nonce used for the actual encrypted messages, and uses the same
xchacha20+poly1305 encryption as is used for PFS+PQ messages.

The plaintext inner payload is identical to a PFS+PQ message bt-encoded with sender Ed25519 pubkey,
content, signature, and optional Pro signature.  The plaintext payload is also null byte padded with
the same padding rules as PFS+PQ messages (but without needing to include PQ ciphertext, the minimum
size of such a message is 256 bytes instead of 1536 bytes).

As with PFS+PQ messages, the content (excluding added padding) is the encoded Protobuf message.

When clients attempt decryption, they first attempt the normal PFS+PQ decyption using the
(supposedly) encrypted `ki` value.  (This is quite unlikely to actually match any current PFS+PQ
keys, but even if it does match, PFS+PQ decryption will fail.)

Upon failure to decrypt using normal PFS+PQ, the client attempts a fallback, non-PFS decryption
using the key/nonce described above.

If this decryption *succeeds* the client should process the message normally, but clients should
provide some indication to the user reading the message that the message decryption fell back to
weakened security.

## Pre-PFS compatibility grace period

Within at least the first 6 months of PFS+PQ being available on all Session clients, Non-PFS
messages do *not* follow the above non-PFS encryption mechanism, but rather use the current "v1"
Session message protocol (which involves multiple layers of independent protobuf encoding around the
Content).

# Migration

Clients that support PFS+PQ and successfully find a PFS+PQ pubkey record for a session account being
messaged should automatically opt-in to using PFS+PQ encryption.  We use the fact that a published
pubkey message exists as an indication that the client's devices supports the new encryption and
message format.

As a result, clients *must not* publish PFS+PQ records until all of their devices are upgraded to
support PFS.  The device group records which devices an account has, but only ever the upgraded
ones: a device that has never joined a group is invisible to it.  So whether every device of an
existing account is upgraded is the user's to declare, and the declaration is recorded as follows.

## The account's message version

Whether every device of an account reads PFS/PQ messages is recorded in the account's user profile
config, under the key `v`: the lowest message protocol version every device of the account can
read.  Absent means 1.  2 means that every device reads PFS/PQ messages, and is what allows the
account to publish its key to namespace -21.

It lives in the user profile rather than in the device group: the profile reaches every device of
the account, old clients included, which keep keys they do not understand; it merges as any other
key does; and it outlives the group being dissolved or replaced.  The group payload cannot be read
by a device until it is admitted, and dies with the group.

A device publishes the account's key to -21 only while all of these hold: `v` is 2 or more, the
device is a member of a device group in good standing, and a fetch of namespace 21 has been merged
(see "Account Key Rotation").  `v` decides publishing and nothing else: every device fetches -21 and
checks what it holds (see "Rogue keys" below), whatever `v` says.

- **New accounts** set `v` to 2 when the account is created, since the account's only device is a
  current one.  An account restored from its recovery phrase sets nothing: what the account says
  arrives from the swarm.
- **Existing accounts opt in.**  The user first builds the device group up -- links every device
  they use, so that a device not in the group is one they are prepared to have miss PFS/PQ messages
  -- and then enables PFS/PQ on a device in the group.  Enabling sets `v` to 2, which reaches the
  account's other devices as any config change does, and has the enabling device publish the
  current account key after its next fetch, without waiting for a rotation.
- **It is one-way.**  `v` is never lowered, and clients offer no way to lower it.  A contact that
  has fetched the account's key goes on using it for as long as its cache keeps it (see "Account
  keys"), whether or not -21 still holds it, so turning PFS/PQ off would take that long to reach
  contacts; and the only reason to want it off, adding a device that cannot read PFS/PQ messages,
  would not be helped by it.

The cutoff is narrow and gradual.  It applies to one-to-one messages only: groups and communities
have encryption of their own.  Messages received before enabling stay readable.  Contacts switch to
PFS/PQ as they fetch the account's key, not all at once.

## Rogue keys

Nothing but the account seed is needed to publish to -21, so a key there that is none of the
account's means that someone outside the account's devices holds the seed.  It is a forgery in the
same class as the others a seed holder can make (see "Displaced devices"), and answered the same
way: by making it seen.

Every member of a device group in good standing checks each key it finds on -21 against the account
keys it holds, current and rotated alike, whatever `v` says: a seed holder publishing a key need not
have set it, and contacts encrypt to whatever they find.  Only such a member judges.  A device
outside the group -- one that has never joined, is asking to, or was removed, displaced, dropped or
dissolved -- holds none of its group's keys, or stale ones, and could not tell a rogue key from its
group's own; it judges nothing, and forgets any key it was still checking when it stops being a
member, since a key seen then may have been rotated away for good by the time it is back.

So that a key published before a device could judge it is still seen, a device that becomes a
member in good standing -- starting a group, having its admission confirmed, or reading its group
again after being displaced or dropped -- forgets where its retrieves of -21 had reached, and
fetches -21 itself at once, reading what it holds from the start.  It fetches rather than waiting
for its next poll because a device subscribed for pushes does not poll, and -21 would send it
nothing until something new landed there.

A key that is none of the member's:

- **Is not judged on sight.**  A key another device of the account has just rotated to reaches -21
  and namespace 21 in separate stores, and a device can see the -21 one first: in one poll whose
  21 retrieve reports more and finishes in a later round, one message at a time through a
  subscription, or with a poll landing between the two stores.  So the device records the key as
  suspect and fetches namespace 21, and only once a fetch sent after the key was seen has drained
  does it decide.  A key that has become known by then was a rotation, and is nothing.  One still
  unknown is rogue.  A suspect is kept across a restart, since -21 is not handed out twice: a
  retrieve resumes after the last message it returned.
- **If rogue, is reported to the user**, who is told that the recovery phrase is in someone else's
  hands.  If `v` is 2 or more, the device also takes its own current key as unpublished, so that its
  next push -- made at once -- puts the account's key back over the rogue one.
- **Is never deleted.**  Deleting it would be a tug-of-war with a holder of the seed, who can
  publish again; as with every other forgery, the protocol makes it seen rather than trying to
  prevent it.

What this leaves open is a swarm member that lags on 21 as well as on -21: the window of the race
itself, accepted rather than closed with a timer.

An account that has forked (see "One group per account") has two groups each publishing its own key,
and each sees the other's as rogue.  That is what it is -- a holder of the seed outside this
group -- and it is settled as any fork is, by the user keeping one group.


# Push notifications

Android and iOS require obtaining the new keys for push notifications to work: new pushed messages
might use a new key that the device has not yet learned about.  However the encrypted account
devices message is much too large to fit into push notifications (and on top of that, neither
Firebase nor APNS guarantee delivery of push notifications to the device).

To work around this, we will require updating Session-ios and -android with code that attempts
decryption using current known keys and, upon failure, initiates an onion routed request to fetch
new account device data messages from the account's swarm.

Both platforms provide approximately 30s to process the request, and both also appear to require
that such a high-priority notification actually produce a notification within that 30s, and so the
design here will:

- identify whether a v1 or a v2 message.  If v1, carry out existing decryption.
- for v2:
  - attempt decryption; if it succeeds with existing recent keys, display the notification (or on
    iOS, mutate the notification to show the decrypted content).
  - if it fails, make a connection to the account swarm to fetch new device account messages,
    process those messages (to learn new keys) and then attempt decryption again.
  - if it succeeds, show the notification content.
  - if it still fails, show an error message ("Could not decrypt incoming message") as the
    notification.
  - (optional) if a recent decryption failed with the same indicated decryption key, cool down for a
    while before going back to the account device key.

# Extension - Pro subscriptions for >4 linked devices on an account

The spec above allows for limits on the number of linked devices for a single account.  This is
intended to be used to allow more accounts for Pro users by having storage server deny linked device
config storage containing more than 4 keys.

This will require modifying storage server to:
- understand and handling Pro proofs for validating the pro status of a requestor
- parsing the outermost linked device configs to determine the number of keys in the message, and
  denying storage for linked device configs with more than 4 keys unless accompanied with a Pro
  proof.
